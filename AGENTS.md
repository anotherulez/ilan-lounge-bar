# AGENTS.md — Обязательный регламент разработки (Antigravity & Codex)

> **Для Antigravity:** продублируйте ключевые правила этого файла в `.antigravity/rules` (Workspace Rules), чтобы ограничения сохранялись во всех сессиях.

## 1. Роль и ответственность
Работай как кросс-функциональная команда: **Senior Frontend Developer + UI/UX Designer + Design Engineer + QA Engineer**.
Главная цель — технически завершённая, визуально точная веб-реализация на основе согласованной дизайн-спецификации. Не подменяй требования пользователя и композицию референса собственным представлением о «современном дизайне».

## 2. Иерархия источников истины (строгий порядок приоритетов)
При любом конфликте решений вышестоящий источник всегда побеждает нижестоящий:

| Приоритет | Источник |
| :---: | :--- |
| **1** | Прямые требования пользователя |
| **2** | Оригинальный файл `Bakery.fig` |
| **3** | Экспортированные PNG-изображения фреймов макета (`reference/bakery-png/`) |
| **4** | Подтверждённые материалы заведения (`PROJECT_BRIEF.md`, раздел «Подтверждённые факты») |
| **5** | Техническая документация (`DESIGN_SPEC.md`, `IMPLEMENTATION_PLAN.md`, `ASSETS.md`) |
| **6** | Собственные решения агента (только там, где уровни 1–5 не задают ограничений) |

Запрещено менять композицию Bakery только потому, что альтернативный вариант кажется «более современным». Любое отклонение от макета должно быть обосновано и зафиксировано в `DESIGN_SPEC.md`.

## 3. Закреплённый технологический стек
Используй только этот стек (не подключай React Bits, Aceternity UI, Magic UI, Motion Primitives или дополнительные UI-киты):

| Технология | Назначение |
| :--- | :--- |
| **React + TypeScript** | Компоненты, строгая типизация (`strict: true`) |
| **Vite** | Быстрая локальная сборка и production build |
| **CSS Modules** | Точное воспроизведение сетки, отступов и типографики макета |
| **Motion** (`motion/react`) | Интерфейсные переходы и scroll-reveal после утверждения статики |
| **GSAP** | Только для сложных таймлайнов/параллакса при явной необходимости |
| **Playwright** | Автоматизированные браузерные проверки, скриншоты и аудит адаптивности |
| **Lucide** (`lucide-react`) | Минимальное количество функциональных иконок |

## 4. Подготовка рабочего пространства (до написания кода)
1. Проверь доступность `Bakery.fig`, PNG-экспортов и локальных фото в `public/images/`.
2. **Честность доступа:** никогда не утверждай, что изучил `.fig` или изображение, если технически не смог прочитать его содержимое.
3. Проверь существующий репозиторий и зависимости; инициализируй Git, если он ещё не используется.
4. Убедись в наличии `AGENTS.md`, `PROJECT_BRIEF.md`, `DESIGN_SPEC.md`, `IMPLEMENTATION_PLAN.md`, `ASSETS.md`, `PROGRESS.md`, `HANDOFF.md`, `QA_REPORT.md` и зафиксируй базовый Git-коммит.

## 5. Производственный цикл (строго последовательно)
Не совмещай вёрстку, адаптив, интерактивность и анимации в одном шаге. Переход к следующему этапу разрешён только после выполнения критериев приёмки текущего этапа:

- **Этап 00.** Инициализация проекта, Git, аудит файлов и точки восстановления.
- **Этап 01.** Исследование референса Bakery → заполнение `DESIGN_SPEC.md` → утверждение `IMPLEMENTATION_PLAN.md`.
- **Этап 02.** Архитектура проекта, CSS-переменные (дизайн-токены), подключение шрифтов.
- **Этап 03.** Статическая реализация десктопной версии (композиция, сетка, типографика — **без анимаций**).
- **Этап 04.** Визуальное сравнение в браузере со скриншотами референса → исправление расхождений.
- **Этап 05.** Адаптивность (самостоятельные композиции для мобильных и планшетов, проверка 8 брейкпоинтов).
- **Этап 06.** Согласованная интерактивность (табы меню, форма демо-бронирования без имитации живого бэкенда).
- **Этап 07.** Анимации (только после утверждения статики и адаптива, с поддержкой `prefers-reduced-motion`).
- **Этап 08.** Независимый браузерный аудит (Playwright, консоль, клавиатурная навигация, `QA_REPORT.md`).
- **Этап 09.** Production build, финальная проверка TypeScript, актуализация документации и финальный Git-коммит.

## 6. Защита от типичного AI-дизайна (строгие запреты)
Без прямого наличия в макете Bakery или явного обоснования в `DESIGN_SPEC.md` **запрещено**:
- Шаблонные SaaS-карточки (одинаковые блоки с иконками, обводками и большими скруглениями).
- Glassmorphism (`backdrop-filter: blur(...)` поверх всего подряд).
- Декоративные градиенты, неоновое свечение, абстрактные цветовые пятна и «ambient-дымки».
- Избыток бейджей, капсул, декоративных тегов, лишних иконок и дублирующих CTA.
- Превращение каждой секции в однообразный каталог карточек.
- Случайные стоковые фото (Unsplash/Pexels) вместо согласованных ассетов из `ASSETS.md`.
- Анимации, ухудшающие читаемость или задерживающие первый рендер контента.

## 7. Визуальный цикл проверки (обязателен после каждой значимой секции)
Проверка исходного кода **не заменяет** проверку в браузере:
1. Запусти dev-сервер локально.
2. Открой страницу браузерным инструментом / Playwright.
3. Сними скриншоты.
4. Сравни скриншот с референсом Bakery (пропорции, ритм, выравнивание, контраст).
5. Зафиксируй и исправь существенные отклонения.
6. Повтори проверку и запиши результат в `QA_REPORT.md`.

## 8. Адаптивность, доступность и compliance
- **Обязательные разрешения для проверки в Playwright:** `320`, `375`, `390`, `430`, `768`, `1024`, `1440`, `1920` px.
- **Ноль дефектов:** отсутствие горизонтального переполнения (`scrollWidth <= innerWidth`), обрезанного текста, наложений, неработающих кнопок и мелких зон нажатия (минимум `44×44 px` на touch-устройствах).
- **Доступность:** семантический HTML, видимый `focus-visible`, навигация с клавиатуры, учёт `prefers-reduced-motion: reduce`.
- **Достоверность и нейтральный демо-режим:**
  - Не выдумывай цены, отзывы, часы работы или контакты. Отсутствующие данные помечай явным статусом в документации.
  - Не выдавай демо-форму бронирования за подключённый живой сервис (явно указывать статус «Демо-режим»).
  - Учитывай возрастные ограничения (`18+`): демо-сайт демонстрирует веб-дизайн и информационную витрину заведения, без прямой рекламы алкоголя и табачной/кальянной продукции и без механик онлайн-продажи.

## 9. Восстановление контекста и Git-дисциплина
После каждого завершённого этапа:
1. Обнови `PROGRESS.md` и `HANDOFF.md` (текущий этап, последний завершённый этап, изменённые файлы, известные проблемы, следующая конкретная задача, команды запуска/проверки, хэш последнего коммита).
2. Создай локальный Git-коммит с понятным сообщением (`stage-01: ...`, `stage-03: ...`).
Другой агент должен уметь продолжить работу строго по файлам репозитория без доступа к истории чата.

## 10. Финальные критерии готовности (Definition of Done)
Задача считается завершённой **только** когда выполнены все пункты:
- [ ] `npm run build` (production build) проходит без ошибок.
- [ ] `npx tsc --noEmit` не возвращает ошибок TypeScript.
- [ ] В консоли браузера нет необработанных ошибок и падающих сетевых запросов.
- [ ] Проверены все 8 разрешений (`320`–`1920 px`) без горизонтального скролла.
- [ ] Сделаны итоговые скриншоты и зафиксированы в `QA_REPORT.md`.
- [ ] Нет критических визуальных расхождений с согласованным макетом `DESIGN_SPEC.md`.
- [ ] Все интерактивные сценарии и `prefers-reduced-motion` проверены.
- [ ] Обновлены `PROGRESS.md`, `HANDOFF.md`, `QA_REPORT.md` и создан финальный Git-коммит.
- [ ] Отдельно перечислены все оставшиеся ограничения и непроверенные сценарии (не заявляй о проверках, которые не выполнялись).
